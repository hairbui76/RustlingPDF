RustlingPDF desktop native-tool notices
=======================================

The desktop bundle contains exactly two external command-line tools: qpdf and
Tesseract OCR. Everything else listed below is linked into those commands or
shipped solely as one of their runtime libraries; none of it is a separately
exposed desktop tool.

Every license text referred to here is shipped next to this file, under
`licenses/` inside the installed bundle (`resources/tools/licenses/` inside
the application package). Where a section names a file such as
`LGPL-2.1.txt`, that file is present in the same directory as this notice.

4. Linux x86_64 — libraries linked into the Tesseract command
--------------------------------------------------------------
The Linux `tesseract` command is built by RustlingPDF's own CI workflow
(`.github/workflows/desktop-tools-tesseract-linux.yml`) from checksum-pinned
official sources, statically linked against musl. It contains, per the version
banner the command itself prints:

  - Tesseract 5.5.3 — Apache License 2.0 — `APACHE-2.0.txt`
  - Leptonica 1.85.0 — BSD-2-Clause — `LEPTONICA.txt`
  - libjpeg-turbo 3.1.0 — BSD-3-Clause, IJG, zlib — `LIBJPEG-TURBO-3.1.0.txt`,
    `LIBJPEG-TURBO-3.1.0-README.ijg.txt`
  - libpng 1.6.46 — libpng License — `LIBPNG.txt`
  - libtiff 4.7.0 — libtiff license — `LIBTIFF.txt`
  - zlib 1.3.1 — zlib License — `ZLIB.txt`
  - musl libc 1.2.5 — MIT — `MUSL-COPYRIGHT.txt`
  - GCC runtime support (libgcc, libstdc++) — GPL-3.0-or-later **with the GCC
    Runtime Library Exception 3.1** — `GPL-3.0.txt` and
    `GCC-RUNTIME-EXCEPTION-3.1.txt`

`tesseract` is a C++ program, so the compiler's own runtime support code —
libgcc's unwinder and libstdc++ (confirmed present in the binary: it exports
`__gxx_personality_v0`, `_Unwind_*` and `__cxa_*`) — is statically linked into
this command. That code is GPL-3.0-or-later, but carries the **GCC Runtime
Library Exception 3.1**, whose entire purpose is to permit its inclusion in
binaries that are not themselves GPL-3.0. Its full text is shipped in
`GCC-RUNTIME-EXCEPTION-3.1.txt` (with the GPL-3.0 text it modifies in
`GPL-3.0.txt`).

No *other* copyleft library is linked into this command. It is built with
`DISABLE_CURL`, `DISABLE_ARCHIVE`, `GRAPHICS_DISABLED` and without the training
tools, so curl, libarchive, giflib, libwebp, OpenSSL and the ICU/pango/cairo
training stack are not present at all. libtiff is built without JBIG, LZMA,
Zstd, WebP and LERC — JBIG-KIT in particular is GPL-2.0-or-later and is
deliberately kept out of the commands we build ourselves.


5. Linux x86_64 — libraries resolved from the host
---------------------------------------------------
Four shared libraries are NOT shipped and are resolved from the user's system
at run time: `libgmp.so.10` (pulled in by the bundled Nettle and Hogweed),
`libstdc++.so.6`, `libgcc_s.so.1` and `libz.so.1`. They are not redistributed
by RustlingPDF, so no notice obligation attaches to them here. The Linux
support floor this implies is stated in
`rust/contracts/desktop-native-startup.md`.

7. Windows x86_64

their transitive PE import closure — not, as an earlier revision of this
notice said, "every DLL adjacent to them". The closure is computed by
`rust/scripts/install-desktop-tools.ps1` by walking the import and delay-import
tables; DLLs the closure does not reach (the ICU, pango, cairo, glib,
HarfBuzz, FreeType and fontconfig stack, which only Tesseract's *training*
tools import, plus five unreferenced MSVC runtime DLLs) are not shipped.

qpdf side — 4 files besides `qpdf.exe`:

    terms that permit redistribution with an application.

Runtime Library Exception 3.1*, which is what permits shipping them alongside
software that is not GPL-3.0. Both texts are shipped.

No GPL-2.0 component is shipped. The upstream installer's `libtiff-6.dll` is the
MSYS2 build compiled `--enable-jbig`, which imports `libjbig-0.dll` (JBIG-KIT,
GPL-2.0-or-later) — the only GPL-2.0 component that ever entered any bundle.
`rust/scripts/install-desktop-tools.ps1` replaces that DLL with RustlingPDF's own
JBIG-free rebuild of the identical libtiff version before it computes the PE
import closure, so `libjbig-0.dll` is never reached and is not staged. The
staging step then walks the import and delay-import tables of every shipped file
and fails the build if any JBIG reference survives. The JBIG-free libtiff is
built and attested by `.github/workflows/desktop-tools-libtiff-windows.yml` and
pinned by SHA-256; its provenance is recorded in
`rust/scripts/desktop-tools/SOURCES.md`.


8. LGPL relinking notice
------------------------
This section is the notice LGPL-2.1 section 6 and LGPL-3.0 section 4 require
for the copyleft libraries listed in section 3.

The libraries below are shipped in the RustlingPDF desktop bundle **as
separate, unmodified, dynamically linked shared objects**. RustlingPDF has not
modified them; it links against them at run time through the normal ELF
dynamic loader.

  Location in the bundle: `resources/tools/qpdf/lib/`
  (inside the installed application directory; the same layout appears as
  `rust/.desktop-tools/current/qpdf/lib/` in a source build)

  - libgnutls.so.30      (GnuTLS 3.7.3, LGPL-2.1-or-later)
  - libnettle.so.8       (Nettle 3.7.3, LGPL-3.0-or-later as elected)
  - libhogweed.so.6      (Nettle 3.7.3, LGPL-3.0-or-later as elected)
  - libtasn1.so.6        (libtasn1 4.18.0, LGPL-2.1-or-later)
  - libidn2.so.0         (libidn2 2.3.2, LGPL-3.0-or-later as elected)
  - libunistring.so.2    (libunistring 1.0, LGPL-3.0-or-later as elected)

You may modify any of these libraries and use your modified version with
RustlingPDF. To do so, build a replacement with the same SONAME as the file it
replaces (for example `libgnutls.so.30`) and overwrite that file in the
directory above. The qpdf executable and `libqpdf.so.30.3.2` locate these
libraries through their ELF RUNPATH entries `$ORIGIN/../lib` and `$ORIGIN`, so
a replacement placed in that directory is picked up with no relinking of
RustlingPDF itself and no other change. This is what satisfies LGPL-2.1
section 6 and LGPL-3.0 section 4 for dynamic linking.

The same applies on Windows to `libiconv-2.dll`, `libintl-8.dll`,
`libidn2-0.dll` and `libunistring-5.dll`, which live next to `tesseract.exe`
in `resources/tools/tesseract/bin/` and are located by Windows' normal
application-directory DLL search; replace the file in place to use your own
build.


9. Source availability
----------------------
RustlingPDF applies no patches to any component below; each is redistributed as
built by its upstream. Where the corresponding source is obtained depends on how
the component enters the bundle:

  * Components RustlingPDF builds itself from source — the Linux/musl and macOS
    `tesseract` and the macOS `qpdf`, and everything statically linked into them
    (Leptonica, libjpeg-turbo, libpng, libtiff, zlib; on Linux also musl and the
    GCC runtime), plus the Windows `libtiff-6.dll` (RustlingPDF's JBIG-free
    rebuild) — are built from the source archives that `SOURCES.md` pins by
    exact URL and SHA-256. That pinned source IS the corresponding source. The
    statically linked GCC runtime (libgcc/libstdc++) is GPL-3.0-or-later with the
    GCC Runtime Library Exception 3.1; its corresponding source is the GCC used
    by the pinned Alpine musl builder (`gcc-mirror/gcc`, and Alpine's own
    packaging), also covered by the written offer below.

  * The Linux qpdf runtime libraries in section 3 (the LGPL GnuTLS, Nettle,
    Hogweed, libtasn1, libidn2 and libunistring) are redistributed from the qpdf
    Linux release archive, which `SOURCES.md` pins by URL and SHA-256. They are
    stripped Ubuntu 22.04 (jammy) builds; their complete corresponding source is
    the Ubuntu jammy source packages of the exact versions listed in section 3,
    available from Ubuntu and from each project upstream, and is covered by the
    written offer below.

  * The Windows MinGW DLLs in section 7 (except `libtiff-6.dll`, above) are NOT
    separately source-pinned. The pinned input for the whole Windows tool set is
    the official Tesseract Windows installer, whose URL and SHA-256 `SOURCES.md`
    records; these DLLs are MSYS2 / MinGW-w64 builds extracted from it. The
    complete corresponding source
    for each is the MSYS2 source package (upstream sources plus MSYS2's PKGBUILD
    and patches) of the exact version the shipped DLL reports — see the
    "Windows x86_64 — GPL/LGPL corresponding source" section of `SOURCES.md`. An
    earlier revision of this notice claimed `SOURCES.md` records "the exact URL
    and SHA-256 of every input"; that was not true of the individual Windows
    DLLs, which are contents of the pinned installer rather than separately
    pinned inputs. This revision corrects that.
